# 15. home-k3s uses a dedicated nginx reverse proxy, not Traefik, for permanent ingress

## Status

Accepted

## Context

ADR 0014 documented that Cilium's Gateway API is broken on `home-k3s`
— the `reserved:ingress` identity's connection to a backend pod never
completes its TCP handshake, reproduced identically on Cilium 1.20.0
and 1.17.18. A follow-up control experiment (`ingress-lab/`) proved
this is scoped specifically to that datapath: an ordinary workload
proxying to `aegis-api` via a plain K3s `NodePort` works cleanly and
deterministically. `home-k3s` needed a permanent replacement, not
another diagnostic.

Two real options were compared, not a feature-list exercise:

**Option B — a dedicated reverse-proxy Deployment** (the architecture
`ingress-lab` already proved): one small `nginx` Deployment/ConfigMap/
Service, Flux-owned like everything else in this repository, exposed
via the same `NodePort` mechanism already tested end-to-end.

**Option C — K3s's bundled Traefik**, deliberately re-enabled. K3s
deploys Traefik through its **own internal Helm-controller addon
mechanism** — manifests auto-applied from
`/var/lib/rancher/k3s/server/manifests/` on the host — not through
Flux. That's a second, non-Git-owned deployment path parallel to the
one this repository uses everywhere else; its version is tied to the
K3s release rather than independently pinned; and its own Gateway API
support adds a second Gateway-API-vs-Ingress surface on top of the one
Cilium already provides (and already has one confirmed defect in).
None of this is disqualifying by itself, but for a single internal
app on a single-node personal host it's real, avoidable operational
weight with no offsetting benefit — this environment has no ecosystem
scale that would make Traefik's IngressRoute CRDs, middleware chains,
or multi-backend routing pay for themselves.

| Criterion | B (nginx) | C (Traefik) |
|---|---|---|
| Datapath proven on this host | Yes — `ingress-lab`, live, 20/20 | Not tested (would likely work, since its traffic isn't Cilium's Gateway API — but unverified) |
| Git ownership | Fully Flux-owned | K3s-addon-owned by default; fighting that to force Flux ownership |
| Upgrade lifecycle | Independently pinned image + digest | Tied to K3s release cadence unless separately managed |
| Operational complexity | One Deployment/ConfigMap/Service | A full ingress controller for one app |
| Debugging burden | Already understood — plain nginx config | New component, new failure surface |

Not chosen: keeping `home-k3s` internal-only (blocks the roadmap this
milestone exists to unblock), waiting indefinitely for a Cilium fix (no
evidence one is coming), or further kernel debugging (`ingress-lab`
already refuted the general-forwarding hypotheses).

## Decision

**Option B.** A small, hardened `nginx` Deployment
(`infrastructure/ingress/home-k3s/`, namespace `ingress-system`)
terminates TLS and routes `api.aegis.home.arpa` /
`grafana.aegis.home.arpa`, exposed via a pinned `NodePort`
(`30080`/`30443` — the same exposure mechanism `ingress-lab` already
proved). Routing is plain nginx `location` blocks in a Git-owned
ConfigMap — no ingress-controller CRDs, no new API surface.

**PKI**: reuses the **same Aegis Development Root CA** dev-kind trusts
(ADR 0011), restored by the new `scripts/bootstrap-pki-home-k3s.sh`
from the same off-cluster material — never a second root. One
development trust domain, same reasoning as ADR 0011: simpler client
trust (a client that already trusts dev-kind's CA trusts home-k3s's
certificates for free), same recovery property, same off-cluster key
never regenerated by routine reconstruction. The larger blast radius
this implies (one compromised key affects both environments) is
accepted explicitly — this remains a development PKI, not a production
one, in both places.

## Rollback plan

Everything here is a Flux-owned Kustomization
(`clusters/home-k3s/ingress.yaml`,
`clusters/home-k3s/observability.yaml`). `git revert` the relevant
commits and Flux prunes the ingress/observability resources back out
automatically — `home-k3s` returns to `kubectl port-forward`-only
access, same as before this milestone, with no host-level state to
manually undo. The broken Cilium Gateway resources were **removed**,
not suspended (freeing ports 80/443 for nginx), but Cilium's
`gatewayAPI` Helm values and the Gateway API CRDs are left in place —
harmless, and restoring the Gateway/HTTPRoute objects for diagnostics
later (e.g. against a future Cilium release) is a small `kubectl
apply`, not a rebuild. ADR 0014 and `ingress-lab/` are both untouched.

## Consequences

- `home-k3s` now has permanent, Git-owned HTTPS ingress for the first
  time — no more `kubectl port-forward` for ordinary access.
- Routing changes (a new path, a new hostname) mean editing a
  ConfigMap, not learning a new CRD — deliberately the simplest option
  for a single-app environment.
- If Cilium ever fixes the `reserved:ingress` defect, migrating back to
  Gateway API is a real option evaluation, not assumed — `ingress-lab`
  stays as the regression test to re-run against a future release
  first.
- Certificate rotation is **not** hands-off: cert-manager reissues the
  Secret automatically, and the mounted volume updates inside the pod
  within kubelet's normal sync window, but nginx does not reload its
  in-memory certificate without an explicit `nginx -s reload` (verified
  live — the ingress kept serving the *old* certificate for several
  minutes after a forced reissue until reloaded). Documented, not
  hidden; see the ingress runbook.
